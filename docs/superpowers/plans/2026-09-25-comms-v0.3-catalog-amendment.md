# Comms v0.3 catalog amendment (A45, tasks G0–G9): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. (The owner's standing rule for this repo: no subagents; the main session executes, test-first, inline.) Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** approved by the owner on 2026-09-25. D1, D2, D4 and D5 are approved; D3 is modified (a staged upload); G1, G5 and G9 are hardened; and the owner added "full admin on both APIs" (G6a). All of it is folded in below.

**Goal:** Close the v0.3 catalog before D39-B, and make it a full admin bridge on both Telegram APIs:
- **Directory:** the owner can add people, contact points and groups over MCP (the `comms_directory_*` tools the owner chose on 2026-09-25);
- **WhatsApp:** the WhatsApp archive becomes reachable over MCP (R-E17);
- **The 13 not-offered tools:** each is implemented, gated honestly by capability, or removed.

After it, no advertised tool answers an unconditional `PROVIDER_UNSUPPORTED`.

**Architecture:** One spec amendment (A45) records every catalog change. The directory tools are thin services over the existing core directory functions (5b-4 and D16), and their provider identities are input-only. WhatsApp groups become destinations with `grp_` refs, so `group_targets` can build a `whatsapp_cloud` target. A per-person context tool reaches `ContextEngine.archive`. Each newly implemented Telegram request passes the RPC review and joins the pinned sets. The catalog pin, the egress matrix, the host-confirmation list and D39-A all move with it.

**Tech Stack:** Python 3.12, `mcp` 2.2.0, Telethon 1.45.0, httpx 0.28.1, SQLCipher, pytest.

**Spec:** `docs/comms-spec-v0.3.md` (rev 2 + R-001), plus **A45** (G0) and **A46** (the owner, 2026-09-26: four admin tools from the 2026 docs, built in G7 and G8). Design: `docs/superpowers/specs/2026-09-24-comms-v0.3-design.md` D.5 (the catalog). Proposal: P §22–35.

## Global Constraints

- **Branch and approvals.** Work on `comms-v0.3-catalog`, off `main` (`bdcefba`). Merge, push and tag push only with the owner's approval.
- **Commits.** Commit only when the full gate log shows `GATE ok=1`. The gate runs ruff with `--no-cache` and formats only `src tests scripts`. Nothing in-tree is written while a gate runs.
- **Secrets.** Never commit, log or print a credential, session or key.
- **Identities (A26 and D36).** A provider identity (a phone number, a Telegram user or chat id, a WhatsApp group id) may be an **input** to a directory tool, and is never in any tool's **output**. Only `comms_admin_identity_inspect` returns identities.
- **Catalog change, done explicitly.** The catalog pin (`tests/mcp/catalog_pin.json`) is regenerated only in G9, and only after A45 is in the spec and preflight-pinned.
- **One copy of each rule.** Identity normalisation (`marked_chat_id`, `e164`), the group rule (`is_group_identity`) and the reader rule (`ContextEngine.reader`) each exist once.
- **Real network code.** Every new MTProto request is recorded in `docs/verification/telegram-rpc-review.md` and pinned in `READ_RPCS`, `WRITE_RPCS` or `ADMIN_RPCS` before its code lands.
- **Audit trail.** Add dated `**Raouf:**` entries to AGENT.md and CHANGELOG.md at the end, and ledger lines per task.

## Review Focus

1. **An AI adds a number it read in an untrusted message** (a prompt injection), then targets it with a campaign. `contact_add` and `destination_create` are host-confirmed (Owner decision D4), and a campaign send is host-confirmed already. The test belongs to G3.
2. **The same identity is added twice**, or added while an opted-out contact exists. The core's `_refuse_second_enabled` refuses it with `ALREADY_EXISTS`; opt-out is permanent until the owner re-enables. G3.
3. **A WhatsApp group identity is given in a Telegram shape**, or the reverse. Normalisation refuses it with `INVALID_ARGUMENT` before any row is written. G1 and G4.
4. **The per-person context route is used to enumerate numbers.** It takes a `rcp_` ref, never an identity, and returns archive items stripped of provider ids. G5.
5. **A newly implemented Telegram read runs on a bot that lacks the right.** It returns the actor's real capability state (`NOT_AUTHORIZED` and the like), never `PROVIDER_UNSUPPORTED` for a right the account could have. G6.

### Task G1: WhatsApp groups are destinations with `grp_` refs

**Files:**
- Modify: `src/comms/core/campaigns/directory.py` (`DESTINATION_TRANSPORTS` gains `whatsapp`; a WhatsApp destination must be a group, `group:<id>`, normalised by one rule), `src/comms/runtime/facades.py` (`group_targets` builds a `whatsapp_cloud` target for a WhatsApp group)
- Test: `tests/core/test_directory.py`, `tests/runtime/test_facades.py`

**Interfaces:**
- Produces: `wa_group_id(raw: str) -> str` in `comms/transports/whatsapp/numbers.py` (the one rule: `group:` plus digits). `group_targets(conn, grp, actors)` returns `{"whatsapp_cloud": ProviderTarget("whatsapp", "whatsapp_cloud", dst, "group:<id>")}` for a WhatsApp group.

**Identity rule (the owner's G1 addition).**
- One delivery identity per `(transport, canonical identity)` (existing), and one enabled destination per identity (existing `_refuse_second_enabled`), and `UNIQUE(groups.destination_id)` (existing). Together these give one `grp_` per provider group per installation. v0.3 has one account per provider; a multi-account installation would add the account to the key, and is out of scope.
- Display names are labels, never identity.
- Group discovery (WhatsApp `GroupDiscovery`, Telegram dialogs) is a read: it never creates a destination and never re-mints a ref. A group that disappears is marked unavailable and disabled, never deleted. Creating a group destination is an owner act (`destination_create`, host-confirmed).

- [ ] **Step 1: Write the failing tests.**
  - Adding a WhatsApp destination `group:120363049891234567` creates a `grp_` at once (R-E16's rule); a phone number is refused as a WhatsApp destination (`DirectoryError`).
  - Adding the same identity again reuses nothing silently: the second enabled one is refused, and the `grp_` never changes.
  - `group_targets` for that `grp_` has exactly `whatsapp_cloud` when WhatsApp is configured, and answers `NOT_CONFIGURED` when it isn't.
  - `comms_context_recent` on it reads the archive (`whatsapp_webhook_archive`), using `CommsArchive` and `ArchiveContext` from E10b.
- [ ] **Steps 2–4:** Watch them fail, implement, watch them pass. Run the full gate, then commit.

### Task G5: Per-person context — `comms_context_person`

**Tool:** `comms_context_person(recipient, transports?, include_group_activity=false, limit, cursor)`. It aggregates the person's direct communication, each item carrying its provenance:
- the WhatsApp direct-message archive (`whatsapp_webhook_archive`);
- the Telegram private conversation: live through the user actor (`telegram_live`, `messages.getHistory` on the user peer, which is already in `READ_RPCS`), or the bot's retained private updates (`telegram_local`);
- campaign history and delivery status (`campaign_store`).

Group activity is **not** searched by default. With `include_group_activity=true`, the person's messages in shared groups are searched within the ordinary P §71 bounds.

Items are stripped of provider ids, with `cmg_` refs and `untrusted_text`. Cursors are `cur_`.

- [ ] **Step 1: Write the failing tests.**
  - An archived DM for a seeded person is served, labelled `whatsapp_webhook_archive`.
  - The number never appears in the output.
  - A person without that transport's contact point answers `NOT_FOUND`.
  - The cursor is client-bound.
- [ ] **Steps 2–4:** Watch them fail, implement, watch them pass. Run the full gate, then commit.

**Rule.** For every tool and every actor, if the actor's API (the Bot API, MTProto, or the WhatsApp Cloud API) implements the semantic operation, it is implemented, and its capability reports the real state (`AVAILABLE`, `NOT_AUTHORIZED`, `ACCOUNT_INELIGIBLE`, `NOT_CONFIGURED`). Only a genuine API gap is B (`PROVIDER_UNSUPPORTED`), named with the reason in the matrix. Examples of A that are easy to miss:
- the bot's join-request list, from its retained `chat_join_request` updates;
- the bot's member lookup (`getChatMember`);
- the bot's chat permissions (`getChat`);
- the bot's forward (`forwardMessage`);
- the user's topic list (`channels.getForumTopics`).
