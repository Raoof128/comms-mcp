# Comms v0.3 A47 (Telegram mark-read and Telegram media, tasks H0–H6): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. (The owner's standing rule for this repo: no subagents; the main session executes, test-first, inline.) Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** drafted 2026-09-26 from the owner's answers to G9's open questions ("1. allow 2. search 2026 docs we will build it 3. search more docs"). Awaiting the owner's approval before H1.

**Goal:**
- **Mark-read:** the Telegram user account marks a person's conversation read, and nothing else is ever marked read.
- **Media:** Telegram media is sendable, downloadable and (for the user account) uploadable on the same staged-bytes rules WhatsApp already uses.

**Architecture:**
- **One tool and one prohibition.** One new tool (`comms_message_send_media`, all three actors) consumes the media. Mark-read lifts one frozen prohibition, narrowly: `messages.ReadHistoryRequest` is reviewed under the operation `message.mark_read` only.
- **Telegram media refs.** They are ordinary `med_` refs minted from context items:
  - user account: the message locator, with the file reference refetched on use;
  - bot: its own `file_id`.
- **Downloads** reuse G8's held-and-paged download.
- **Uploads** reuse D3's staging (`upl_`), and G8's `saveFilePart` path for group photos.

**Tech Stack:** Python 3.12, `mcp` 2.2.0, Telethon 1.45.0 (layer 229), Bot API 10.3, Graph v26.0, httpx 0.28.1, SQLCipher, pytest.

**Spec:** `docs/comms-spec-v0.3.md` A47 (pinned in the rulings register with R-G9b). Actor matrix: `docs/verification/comms-v0.3-actor-matrix.md`.

## Global Constraints

- **Branch and approvals.** Branch `comms-v0.3-a47` off `comms-v0.3-catalog` (`comms-v0.3-catalog-amendment`), or off `main` once the catalog branch lands. Merge, push and tag push only with the owner's approval.
- **Commits.** Commit only when the full gate log shows `GATE ok=1`, and write nothing in-tree while a gate runs.
- **Secrets.** Never commit, log or print a credential, session, key, bot token or file URL; a Bot API file URL contains the token.
- **Identities (A26).** A `file_id`, a file reference, a peer id or a message locator is an identity and never appears in an output. Only refs go out.
- **Real network code.** Every new MTProto request goes into `telegram-rpc-review.md` and `WRITE_RPCS`, `READ_RPCS` or `ADMIN_RPCS` before its code lands. Every new Bot API method goes into the bot's reviewed set.
- **The frozen prohibition moves only as A47 says.** `ReadHistoryRequest` is sanctioned in the adapter under `message.mark_read`. `channels.ReadHistoryRequest`, `ReadMessageContentsRequest`, `ReadMentionsRequest`, `ReadReactionsRequest` and `GetMessagesViewsRequest` stay prohibited. `mcp.retrieval` still refuses `ReadHistoryRequest`.
- **Bounds.** Staging stays capped at 16 MiB. The bot refuses a photo over 10 MB, and WhatsApp refuses an image over 5 MB, before any call. User slices are 512 KiB and never cross a 1 MiB boundary.
- **Audit trail.** Add dated `**Raouf:**` entries to AGENT.md and CHANGELOG.md, one ledger line per task, and rulings R-H*.

## Review Focus

1. **An expired file reference mid-download.** The user download refetches the message once and resumes from the same offset; a second expiry is `PROVIDER_UNAVAILABLE`, never a loop.
2. **A replayed send-media after a crash between upload and send.** The replay answers from the executor's record and uploads nothing twice. The random_id is derived from the `req_`, as sends already do.
3. **A `med_` from one actor used by another.** A bot `file_id` sent by the user account, or the reverse, is refused `INVALID_ARGUMENT` before any call.
4. **A CDN redirect or `FILE_MIGRATE_X` on download.** It is refused `PROVIDER_UNSUPPORTED`, never followed.
5. **Mark-read reached from a read path.** A context read or a search never sends `ReadHistoryRequest`; the phase-4 test and the operation allowlist both pin this.

## Not in A47

- **Campaign media.** A campaign with media still renders to nothing; the transports' delivery adapters send text only. It needs its own amendment: where the bytes live between freeze and delivery, and whether a generation pins them.
- **Channels (broadcast) as media targets, and albums (`sendMediaGroup` / `messages.sendMultiMedia`).**
- **Videos, voice notes, stickers and animations.** `kind` stays `photo` or `document`, and a later amendment widens it.
