# Comms v0.3 A47 (Telegram mark-read and Telegram media, tasks H0–H6): implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. (The owner's standing rule for this repo: no subagents; the main session executes, test-first, inline.) Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** drafted 2026-09-26 from the owner's answers to G9's open questions ("1. allow 2. search 2026 docs we will build it 3. search more docs"), then run through a developer-docs gauntlet at the owner's request ("search more and gauntlet the plan"). The eighteen findings are in the Gauntlet section below; each one is folded into its task. Awaiting the owner's approval before H1.

**Goal:**
- **Mark-read:** the Telegram user account marks a person's conversation read, and nothing else is ever marked read.
- **Media:** Telegram media is sendable, downloadable and (for the user account) uploadable on the same staged-bytes rules WhatsApp already uses.

**Architecture:**
- **One tool and one prohibition.** One new tool (`comms_message_send_media`, all three actors) consumes the media. Mark-read lifts one frozen prohibition, narrowly: `messages.ReadHistoryRequest` is reviewed under the operation `message.mark_read` only.
- **Telegram media refs.** They are ordinary `med_` refs minted from context items:
  - user account: the message locator, with the file reference refetched on use;
  - bot: its own `file_id`.
- **Downloads** reuse G8's held-and-paged download.
- **Uploads** reuse D3's staging (`upl_`), and G8's `saveFilePart` path for group photos.

**Tech Stack:** Python 3.12, `mcp` 2.2.0, Telethon 1.45.0 (layer 229), Bot API 10.3, Graph v26.0, httpx 0.28.1, SQLCipher, pytest.

**Spec:** `docs/comms-spec-v0.3.md` A47 (pinned in the rulings register with R-G9b). Actor matrix: `docs/verification/comms-v0.3-actor-matrix.md`.

## Global Constraints

- **Branch and approvals.** Branch `comms-v0.3-a47` off `comms-v0.3-catalog` (`comms-v0.3-catalog-amendment`), or off `main` once the catalog branch lands. Merge, push and tag push only with the owner's approval.
- **Commits.** Commit only when the full gate log shows `GATE ok=1`, and write nothing in-tree while a gate runs.
- **Secrets.** Never commit, log or print a credential, session, key, bot token or file URL; a Bot API file URL contains the token.
- **Identities (A26).** A `file_id`, a file reference, a peer id or a message locator is an identity and never appears in an output. Only refs go out.
- **Real network code.** Every new MTProto request goes into `telegram-rpc-review.md` and `WRITE_RPCS`, `READ_RPCS` or `ADMIN_RPCS` before its code lands. Every new Bot API method goes into the bot's reviewed set.
- **The frozen prohibition moves only as A47 says.** `ReadHistoryRequest` is sanctioned in the adapter under `message.mark_read`. `channels.ReadHistoryRequest`, `ReadMessageContentsRequest`, `ReadMentionsRequest`, `ReadReactionsRequest` and `GetMessagesViewsRequest` stay prohibited. `mcp.retrieval` still refuses `ReadHistoryRequest`.
- **Bounds.** Staging stays capped at 16 MiB. The bot refuses a photo over 10 MB before any call. WhatsApp refuses an image that is not JPEG or PNG, or is over 5 MB, and a document outside Meta's type list, before any call. User download slices are 512 KiB at 512 KiB offsets, with `precise` unset, so none crosses a 1 MiB boundary (Gf9). A caption is at most 1024 UTF-16 code units on every actor, with no entities (Gf11).
- **One copy of the part upload.** `saveFilePart` with `inputFile` is used up to 10 MB, and `saveBigFilePart` with `inputFileBig` above it. This rule exists once, and G8's group photo, H4's send and H5's upload all use it (Gf6).
- **Audit trail.** Add dated `**Raouf:**` entries to AGENT.md and CHANGELOG.md, one ledger line per task, and rulings R-H*.

## Review Focus

0. **A file stored on another data centre.** A person's photo usually lives on their own DC. The download goes to `photo.dc_id` / `document.dc_id` over a reviewed borrowed sender, so it is never refused and never loops on `FILE_MIGRATE_X` (Gf1).
1. **An expired file reference mid-download.** The user download refetches the message once and resumes from the same offset; a second expiry is `PROVIDER_UNAVAILABLE`, never a loop.
2. **A replayed send-media after a crash between upload and send.** The replay answers from the executor's record and uploads nothing twice. The random_id is derived from the `req_`, as sends already do.
3. **A `med_` from one actor used by another.** A bot `file_id` sent by the user account, or the reverse, is refused `INVALID_ARGUMENT` before any call.
4. **A CDN redirect or `FILE_MIGRATE_X` on download.** It is refused `PROVIDER_UNSUPPORTED`, never followed.
5. **Mark-read reached from a read path.** A context read or a search never sends `ReadHistoryRequest`; the phase-4 test and the operation allowlist both pin this.

| Gf3 | `FLOOD_PREMIUM_WAIT_X` throttles a non-Premium account's downloads. | `/api/files`, `upload.getFile` | Classified as a rate limit with `retry_after`. |
| Gf4 | "A file can have different valid `file_id`s even for the same bot", and `file_unique_id` "can't be used to download". | Bot API, "Sending by file_id", `PhotoSize` | The bot's `med_` is keyed by `file_unique_id`; `file_id` is kept privately and purged with retention. |

| Gf6 | Above 10 MB, upload with `saveBigFilePart` and `inputFileBig`. Staging allows 16 MiB, and G8's photo helper uses `saveFilePart` only. | `/api/files`, `upload.saveBigFilePart` | One part-upload helper; G8's group photo moves onto it. |
| Gf7 | `inputMediaUploadedDocument` always requires `mime_type` and `attributes`. | constructor page | `force_file`, and a neutral `DocumentAttributeFilename` derived from the MIME type. |
| Gf8 | A photo downloads by `inputPhotoFileLocation` with `thumb_size` set to a `PhotoSize` type; a document with `thumb_size=""`. | `/api/files` | The largest size type, skipping stripped and path sizes. |

| Gf11 | Captions: the Bot API allows 0–1024 characters after entity parsing; `caption_length_limit_default` is 1024 (4096 with Premium); Meta allows 1024. | Bot API; `/api/config` | 1024 UTF-16 code units on every actor, and no entities. |

| Gf15 | **An uploaded file has no message to refresh from.** A file reference is refreshed from its source (for a message, `messages.getMessages` / `channels.getMessages`), and the docs give no lifetime. A `messages.uploadMedia` result has no message behind it. | `/api/file-references`, `messages.uploadMedia` | An expired upload is `NOT_FOUND` ("upload again"), never retried. |
| Gf16 | `messages.uploadMedia`'s peer "can be `inputPeerEmpty` for bots and `inputPeerSelf` for users". | method page | Unchanged (`inputPeerSelf`). |
| Gf17 | A bot photo's width plus height must be at most 10000, with a ratio of at most 20. | Bot API `sendPhoto` | The provider's refusal is classified; nothing decodes images. |

### Task H3: Telegram download

**Files:**

  - `upload.GetFileRequest` with `inputPhotoFileLocation`, whose `thumb_size` is the largest `PhotoSize` type, skipping stripped and path sizes, or with `inputDocumentFileLocation` and `thumb_size=""` (Gf8);
  - `cdn_supported` and `precise` both unset (Gf2, Gf9);

The operation's allowlist is enforced on that sender too. The Telethon private surface it relies on is pinned against the installed source, as E10a pinned `UPDATE_RPCS` (Gf1)., `src/comms/services/media.py` (the download dispatches on the ref's transport), `docs/verification/telegram-rpc-review.md`.

- [ ] **Step 1: Failing tests.**

  - User: aligned 512 KiB slices up to the size.
  - `FILE_REFERENCE_EXPIRED` is refetched once, and a second expiry is refused.
  - A file on DC 4, when home is DC 2, downloads through the borrowed sender. An unexpected `FILE_MIGRATE_X` is followed once to DC X, and a second one is refused `PROVIDER_UNAVAILABLE` (Gf1).

**Files:**

- `src/comms/mcp/egress.py`;
- `.claude/settings.json` (host confirmation, by R-A20's rule);

- [ ] **Step 1: Failing tests.**
  - Each actor sends from a staged file and from a held `med_`.
  - The staged file is taken once, and a replay by `req_` uploads and sends nothing.
  - A crash seam between the upload and the send resolves without a second message.
  - Limits are refused before any call:
    - a bot photo over 10 MB;
    - a WhatsApp image over 5 MB, or not JPEG or PNG;
    - a caption over 1024 UTF-16 code units.
  - A `med_` whose kind is not the requested `kind` (a document sent as a photo) is refused before any call, because neither API can change a file's type (Gf5).
  - A user document is sent as `inputMediaUploadedDocument` with `force_file`, its `mime_type`, and one `DocumentAttributeFilename`. The file name is neutral, derived from the MIME type (`file.pdf`), never a caller's string (Gf7).
  - A 12 MiB staged file goes up by `saveBigFilePart` / `inputFileBig`, and a 3 MiB one by `saveFilePart` / `inputFile` (Gf6).
  - A WhatsApp `med_` past Meta's validity (30 days after upload, 7 days for a webhook's media) is refused `NOT_FOUND` before any call (Gf10).
  - `PHOTO_INVALID_DIMENSIONS`, and the bot's dimension rules (a width plus height of at most 10000, and a ratio of at most 20), are classified `INVALID_ARGUMENT` from the provider's answer. They are not pre-checked, because nothing decodes the image (Gf17).
  - The file's bytes reach no request digest (the executor's `_digestible`).

## Not in A47

- **Campaign media.** A campaign with media still renders to nothing; the transports' delivery adapters send text only. It needs its own amendment: where the bytes live between freeze and delivery, and whether a generation pins them.
- **Channels (broadcast) as media targets, and albums (`sendMediaGroup` / `messages.sendMultiMedia`).**
- **Videos, voice notes, stickers and animations.** `kind` stays `photo` or `document`, and a later amendment widens it.
